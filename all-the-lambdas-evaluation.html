01 · Executive verdict

The project’s heart is real.

This is not a pile of disconnected Church encodings. It is a sustained attempt to make one computational world out of functions alone, then pressure-test that world with arithmetic, lists, algorithms, runtime contracts, coercions, binary representations, rational numbers, and closure-built data structures.

λ

The premise succeeds

Using Lazy Racket as the reduction engine is the right choice for this project. It lets the material begin after the introductory interpreter lesson and spend its attention on construction, representation, invariants, recursion, and composition.

≠

The boundaries are not honest yet

Division by zero, absent search results, negative integer exponents, and noncanonical binary values are handled inconsistently. In several places the project returns a valid-looking answer where the mathematics says the operation is undefined.

↗

The extension surface is exceptional

The existing layers are not dead ends. They support several legitimate futures: languages, types, coercion theory, persistent data structures, binary algorithms, lazy streams, exact computation, and comparative encoding experiments.

Direct recommendation: do one foundation-integrity phase before opening another large branch. Then choose strings and parser combinators as the next major content track, leading to lambda terms represented as ordinary project data. That path exercises almost everything already built without turning the whole repository into an interpreter project.

02 · Project identity

Lambda is the material, not the prerequisite lesson.

The repository makes a valuable pedagogical bet: its learner already understands variables, abstraction, application, and beta reduction. It therefore does not need to spend its energy building another evaluator before it can discuss the structures that evaluators usually demonstrate.

What the project is

  • An executable notebook for constructing computation from lambdas.
  • A comparative laboratory with raw, sugared, strict-contract, and coercive surfaces.
  • A representation study: unary Church naturals, signed pairs, rational pairs, and binary digit lists.
  • A place where higher-order functions are both subject matter and implementation mechanism.

What it should not become

  • A beginner introduction that repeats what the intended learner already knows.
  • A general Racket utility library with lambda encodings hidden behind host conveniences.
  • A monolithic interpreter whose implementation replaces the project’s existing constructed world.
  • An abstraction catalog in which new names arrive faster than concrete examples and laws.
Intended learner already has What the project currently supplies What the next teaching layer should supply
Untyped lambda-calculus syntax and reduction Real programs made of encodings, recursion, and eliminators Representation invariants and worked traces through nontrivial programs
Church booleans and numerals, at least conceptually Arithmetic, signed integers, rationals, lists, and algorithms Explicit contrasts between alternative representations and their operational costs
Comfort with higher-order functions Maps, folds, filters, fixed points, runtime wrappers, and closures Prediction prompts, exercises, laws, and “why this representation” checkpoints

The right product description is an advanced executable lambda-calculus lab. Calling it a course would currently overstate its sequencing and learner guidance; calling it a code collection would understate its coherence and pedagogical potential.

03 · Architecture

One substrate, several lenses.

The repository is best understood as a shared lambda-built core viewed through several semantic and representational lenses. The branches are related, but they are not simply versions on one linear ladder.

Why Lazy Racket is appropriate

The project depends on non-strict behavior for Church booleans and recursive constructions. Racket’s lazy language evaluates applications by need and forces promises when their values are required. That gives the repository a trustworthy reduction substrate without inventing a second semantics in a home-grown interpreter.

What “pure” means here

The computational representations are built from lambdas, application, and pairs encoded as selectors. Host strings, numbers, conditionals, and effects appear where the project explicitly crosses into macro expansion, reading, printing, error display, tests, or demonstrations. That is a credible, teachable boundary—not a claim that every byte in every module is literal lambda syntax.

04 · What works

The repository has earned the right to keep going.

The audit found substantial working content, not merely promising scaffolding. These are the parts to preserve while correcting the foundations.

A coherent constructed world

Booleans select, pairs store, lists recurse, numerals iterate, signed numbers pair sign with magnitude, rationals compose signed numerators with denominators, and algorithms consume those representations. Later layers reuse earlier ideas rather than resetting the model.

Correct core behavior

On valid domains, logic, Church arithmetic, recursion, list transformations, signed arithmetic, rational reduction and ordering, and the principal binary operations all survive direct execution and a broad automated suite.

Binary values prove scale

The binary-list branch moves the project beyond “toy unary arithmetic.” It handles values through the sextillion-scale fixtures and exposes genuine carry, borrow, comparison, multiplication, and long-division questions.

Strict typing is described honestly

The strict branch is presented as runtime tagging and contract enforcement, not as static typing or System F. That precision matters: the teaching value is in the wrappers, checks, error paths, and observable boundaries.

Option and Result are good seeds

Their encodings, readers, and nested behavior are sound. They are exactly the vocabulary the rest of the project needs for absence and partiality; the current issue is limited integration, not a bad foundation.

The test runner is serious

One command discovers the main test modules, treats crashes as failures, preserves a nonzero exit status, and runs in CI. The green total is useful evidence even though it is not yet evidence for every branch or invariant.

The closure demonstration also runs as documented: object-style updates, FIFO and ordered queues, and binary-tree traversal all produce the expected values. Its weakness is isolation, not failure.

05 · Audit method

The evaluation used the project as a learner would—and as a library would.

A green suite alone cannot answer whether examples teach the truth, whether advertised paths load, or whether readers conceal malformed representations. The audit combined source review with direct execution at several boundaries.

Static review

  • Read the README, roadmap, repository guidance, macro layer, implementation modules, test helpers, CI, and test sources.
  • Checked mathematical definitions, comments, contracts, examples, representation claims, and branch-to-branch consistency.
  • Scanned non-test computational modules for host-language constructs outside declared boundaries.
  • Compared labels in tests with the expressions those tests actually execute.

Executable review

  • Ran the complete test runner after the integrity queue: 1,807 passes, zero reported failures.
  • Loaded every non-test Racket module independently to find branches outside test discovery.
  • Used isolated timeouts to distinguish nontermination from slow execution.
  • Probed internal binary digit shapes, typed readers, safe indexing, rational zero behavior, and closure-demo outputs.

Dotenv files were categorically excluded from discovery and inspection. They were not needed for this audit. The audit baseline was main at commit 7098e7b, before this report was added. Counts describe that project content in scope, not Git internals or secret-bearing environment files.

06 · Confirmed findings

The green suite hides a small number of foundational contradictions.

Findings are ranked by pedagogical and semantic impact, not by how many lines a repair would take. “High” means a learner can be taught a false rule, hit a nonterminating advertised operation, or fail to enter an advertised branch.

F-01 · Traversability High

The recommended raw on-ramp was broken at bitter/lists.rkt (resolved).

Resolution: Integrity Phase 2 restored the raw pair/nil definitions, corrected mixed-sign integer addition, and added a discovered bitter/tests/ suite. The focused route passes 10/10 tests and all seven library modules plus the human-readable demonstration load successfully.

At audit time, the README recommended beginning in bitter/, but that branch had commented out its local pair and nil definitions without importing replacements. Loading stopped at the first pair use with pair: unbound identifier; dependent integer and algorithm modules failed for the same reason.

Why it mattered: the project’s pedagogically purest route was also the first route a learner was explicitly told to take, while no bitter module was then under test discovery.

Evidence and repair direction
  • README.md:146 recommends starting with bitter logic.
  • bitter/lists.rkt:38–53 had commented out pair and nil; the first unresolved use was near line 84.
  • bitter/test.rkt, bitter/integers.rkt, and bitter/algorithms.rkt consequently did not load.
  • Mixed-sign addZ also subtracted magnitudes in reverse order, mapping +5 + −2 to 0 rather than 3.

The completed repair restored the local representation, corrected mixed-sign addition, and gave the branch its own smoke and regression tests so this route cannot drift silently again.

F-02 · Mathematical semantics Medium

Division by zero follows deliberately different, now-declared policies.

Raw and strict runtime-tagged Church natural and integer division do not terminate. Coercive natural and integer division returns an explicit error. Binary division returns quotient zero and the original dividend as remainder. Raw Church-backed and binary-backed rationals deliberately treat a zero numerator or denominator as rational zero; the strict and coercive runtime-tagged rational boundaries now return explicit errors for a divisor that meets that raw zero definition.

Resolution: each choice is coherent within its layer. The README, implementation comments, and repository guide now tell a learner which domain uses which policy, including when changing a representation or runtime wrapper changes whether an operation returns, errors, or does not terminate.

F-03 · Termination and absence High

Binary search can repeat forever and its natural “not found” value is not a natural.

The natural-number search tracks both bounds as Church naturals. When the target is lower than the first element and the midpoint is zero, pred zero is still zero, so the recursive state does not change. When another absence path does terminate, the untyped function returns Church true as a sentinel even though the typed wrapper labels the result as a natural.

Why it matters: the function’s two failure modes are respectively nontermination and a malformed typed value. “Not found” is expected data and should be represented as Option.

Concrete failing scenarios
  • Searching below the first element of a nonempty natural list exceeded a four-second isolated timeout.
  • Typed search for 2 in the sorted natural list [1, 3] reached the reader as a procedure tagged nat, then failed with number->string: expected number?.
  • The empty-list upper-bound initialization has the same natural-underflow problem.

A safe redesign can use half-open bounds [low, high), terminate when they meet, and return some(index) or none. That removes both the underflow and sentinel.

F-04 · Representation invariant High

Public binary arithmetic violated its canonical representation (resolved).

Resolution: Integrity Phase 4 made all-zero normalization return canonical [0], normalized generated division quotients, and added direct structure checks across the binary-natural boundary and its signed-integer and rational consumers.

At audit time, repository guidance said binary naturals had no leading zeroes and public arithmetic returned normalized output. Direct structure probes contradicted that claim: bin-div 4 3 produced the little-endian digit list [0,0,1] rather than [1], while bin-sub 4 4 produced the empty list rather than the declared zero representation [0].

Why it mattered: the public reader collapsed both malformed forms to the right host number, so value-only tests could not see the invariant failure. Later algorithms can depend on shape, not merely value.

Repair direction

The completed repair makes [0] the one canonical zero, normalizes division, and uses direct digit-list assertions rather than relying exclusively on bin-read.

F-05 · Domain precision Medium

Negative integer exponents return zero, which is a false answer rather than an integer result.

Both unary and binary signed-integer exponentiation choose zero whenever the exponent is negative. Thus 2^-1 reads as 0. Negative powers generally leave the integers; the operation is partial in this domain, not truncated in the way integer division is.

Better semantic choices

The cleanest integer API returns a Result error for negative exponents. A second, explicitly lifted operation can return a rational. Either choice teaches the domain boundary; silently returning zero erases it.

F-06 · Contract integrity Medium

The strict layer has two holes in otherwise useful runtime contracts.

IND-OPT unwraps its arguments to check the range before confirming that they are a typed list and typed natural. The probe IND-OPT FALSE ZERO returns option:none instead of a type error. Separately, typed natural and integer readers emit the boolean error object when given the wrong type; nat-read TRUE becomes err:bool.

Why this is pedagogically useful to fix

These are small examples of a large systems lesson: a wrapper is only a boundary if every path goes through it. Repairing them can become a worked chapter on validation order, error provenance, and the difference between “invalid input” and “valid input with no answer.”

F-07 · Evidence quality Medium

Several test names do not describe the expressions they execute.

Partial resolution: Integrity Phase 1 corrected the approved strict, coercive, and binary arithmetic claims. Additional mismatches listed in the roadmap remain outside that phase's authorized boundary.

At audit time, a strict test labeled DIV ZERO FOUR executed division by one; multiplication and subtraction labels sometimes executed different operands; one binary “unnormalized versus normalized” equality test compared bin-one with itself; list append and fold labels similarly drifted from their expressions.

Why it matters: every assertion can pass while the named teaching example was never run. Test names are learner-facing claims in this repository, not incidental metadata.

Evidence policy to add
  • Prefer table-driven fixtures where the label is derived from the same operands used by the expression.
  • Add explicit structural and law-based suites rather than many hand-copied near-duplicates.
  • Test documentation examples verbatim when possible.
  • Keep the current assertion total, but stop treating it as complete branch coverage.
F-08 · Teaching precision Precision

A cluster of comments and examples teaches the wrong local fact.

Examples include a two-element list expansion that repeats a instead of using b, a typed-boolean example that uses Church one as if it were Church true, a bare empty list described as a fully typed list, predicate comments that name their input type as their return type, and a NOR section labeled XOR.

None of these destroys the project’s main thesis. Together, though, they impose avoidable verification work on exactly the learner who is trying to reason from representation details.

Related precision notes
  • Rational exponentiation is explicitly defined as base raised to the floor of the rational exponent. The implementation and tests agree, but the public name can still invite a stronger mathematical reading. Consider naming the restriction at the API boundary.
  • The strict list tag is shallow: lists can intentionally contain mixed typed elements. That is a legitimate experiment, but “strict” should not imply homogeneous element typing.
  • The closure-data-structure file is an effective demo, but it is not a provided module, has no automated tests, and does not yet explain representation or persistence laws.

No findings match that search.

07 · Pedagogical evaluation

Strong material; incomplete learning path.

The repository should not backfill an introduction to lambda calculus. Its missing pedagogy begins after that point: how a learner chooses a route, sees an invariant, predicts a program, diagnoses a boundary, and compares two encodings of the same idea.

Journey A · Construction

Raw logic → Church naturals → fixed-point recursion → pairs and lists → signed values → rationals. The question is: “How does one representation become enough substrate for the next?”

Journey B · Semantics

The same operations through untyped, strict-contract, and coercive surfaces. The question is: “Where does invalid input become an error, a conversion, a default, or divergence?”

Journey C · Representation

Unary numerals → binary digit lists → signed binary values → binary rationals. The question is: “What changes when data representation changes but the mathematical value does not?”

Add a pedagogical spine without turning modules into textbooks: a short goal, prerequisites, the representation invariant, one worked trace, two prediction exercises, and a pointer to the next branch. That small repeated structure would make the project navigable while preserving its exploratory character.

10 · Branch map

A stable trunk should feed several independent limbs.

This dependency map explains why “strings and parsers next” is a direct recommendation without pretending every other path must wait behind it.

Why the language limb wins the next-major-branch decision: it reuses the widest range of existing ideas—lists, pairs, recursion, higher-order composition, Option/Result, errors, and eventually maps— while producing a visible new capability. It also gives the project a natural way to study its own source objects later without making an interpreter the price of entry.

11 · Recommended sequence

Repair trust first; then grow one flagship branch while the others remain available.

This is a dependency order, not a calendar estimate. Each phase should be split into the repository’s normal single-pass executable chunks when it becomes implementation work.

Phase 0

Foundation integrity

Restore bitter, establish a single partiality policy, fix search termination, enforce binary and rational invariants, repair strict validation holes, and extend CI to every advertised branch.

Phase 1

Pedagogical spine

Build the dependency index and repeatable chapter frame. This can proceed alongside foundation work, but learner-facing examples should not be finalized until repaired semantics are stable.

Phase 2

Strings and parser combinators

Introduce encoded text, safe observations, parser primitives, structured failures, and an arithmetic grammar. This becomes the flagship “new capability” branch.

Parallel

Binary algorithms and complexity

Once canonical forms are reliable, add law-based conversions, exponentiation by squaring, and operation counts. This track is independent enough to run without waiting for the language branch.

Phase 3

Lambda terms as data

Add syntax values, binding operations, substitution, strategies, parsing, and printing. Keep it explicitly scoped as one branch of the larger constructed world.

Choose

Deepen systems or data structures

Choose based on the teaching question that feels alive then: strict/coercive semantic boundaries, or persistent structures and graph algorithms. Neither choice invalidates the other.

Later

Streams, exact computation, and abstractions

Streams should precede computable reals. Generic algebraic interfaces should follow multiple mature examples. These become culminations, not foundations.

12 · Definition of done

Every new branch should leave evidence, not just definitions.

The project’s next stage needs a shared completion standard so that breadth does not recreate the current branch drift.

  • Domain: valid, invalid, absent, and divergent-looking cases are explicitly classified before implementation.
  • Representation: constructors, invariants, canonical forms, and reader boundaries are stated in learner-facing prose.
  • Purity: every host-language escape is confined to an identified reader, printer, macro, test, or demonstration boundary.
  • Execution: every advertised module loads independently and is discovered by CI.
  • Evidence: examples test structure and laws as well as rendered final values.
  • Termination: recursive APIs have a stated decreasing measure or productivity argument and at least one boundary test.
  • Pedagogy: the learner gets a goal, prerequisites, invariant, worked trace, prediction exercise, and next-route link.
  • Comparison: when a parallel representation exists, at least one example explains the operational or semantic tradeoff.
  • Scope: a branch earns its new abstractions and dependencies through real use sites; no convenience package or vocabulary arrives without a teaching payoff.

Ship gate for the foundation phase

All README-recommended modules load; zero denominators cannot produce rationals; division-by-zero and negative integer powers are explicit errors; search returns Option and terminates; every public binary result is canonical; strict wrappers validate before unwrapping.

Ship gate for any new extension

The branch has a runnable learner journey, a stable observable boundary, ordinary examples, boundary examples, law or differential tests, and a clear explanation of why its representation belongs in a lambda-calculus project.

A useful checkpoint for any eventual exact-real representation: approximation must come with precision and correctness guarantees.

Greg Michaelson: An Introduction to Functional Programming Through Lambda Calculus

The project’s existing linked book remains a broad contextual resource; this repository’s opportunity is to go beyond its introductory role.
